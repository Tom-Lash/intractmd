# IntractMD — Project Rules for Claude Code

Read this before making any change in this repository.
It supersedes all earlier instruction files in this folder.

## What this project is

IntractMD is a drug-interaction and polypharmacy risk platform (Resolve Medical LLC).
Node.js v22, Express, deployed on Render with auto-deploy from `main`.

Four public surfaces:

| Path | File | Notes |
|---|---|---|
| `/` | `public/index.prod.html` | Patient checker — **off limits, see below** |
| `/proactive` | proactive surface | Supplement screening, pilot-gated |
| `/clinical` | clinical surface | MTM workflow, pilot-gated |
| `/deprescribing` | deprescribing surface | CPRS counterfactual simulation, pilot-gated |

The three pilot-gated surfaces sit behind HTTP Basic Auth driven by the
`PILOT_USERS` environment variable in Render. The patient surface at `/` is
never gated.

All proprietary scoring logic stays server-side. Do not move CPRS logic,
thresholds, or the drug-pair database into client-side code.

## Hard rules — never violate these

1. **Never edit `public/index.src.html` or `public/index.prod.html`.**
   These are patched by hand outside of Claude Code. If a change is needed in
   either file, stop and produce a diff for the human to apply manually.
   Do not edit them "just this once," and do not edit them as a side effect of
   a broader refactor.

2. **Never run `obfuscate.sh`, and never edit it.**
   This overrides any older instruction in this repo saying that
   `index.prod.html` is generated by running the obfuscator. That is no longer
   true. Block 2 contains a top-level `await` that the obfuscator mangles, so
   running it breaks production. `index.prod.html` is now maintained by direct
   hand-patching instead.

3. **Never push directly to `main`.** Branch protection is enabled and direct
   pushes will be rejected. Every change goes through a branch and a pull
   request.

4. **Always run `node --check` on any JavaScript file before committing it.**
   If it fails, fix it before proceeding. Never commit a file that has not
   passed this check.

5. **Never commit secrets.** API keys, the GA service-account JSON, and
   `PILOT_USERS` values live in Render environment variables or in
   `~/.config/intractmd/`, never in the repo.

6. **Never issue treatment directives in patient-facing output.**
   Do not generate text telling a user to discontinue, stop, reduce, switch, or
   start a medication. Describe the finding and direct them to their prescriber
   instead. Every piece of patient-facing advice must end with a prompt to
   consult their prescriber before altering their regimen. This is a floor, not
   a substitute for non-directive wording.

## Why the HTML files are fragile

`index.src.html` and `index.prod.html` use a multi-block obfuscation
architecture. Any direct modification to `index.prod.html` risks JavaScript
syntax errors that take down the entire platform — there is no build step left
to catch them. This is why those two files are edited only by hand, deliberately,
outside of an agent session.

## Files that are safe to modify

- `server.js`
- `scripts/`
- `package.json`
- `.env.example`
- the three pilot-gated surface files
- new files you create (for example `i18n.js`)

Anything not on this list: ask before touching it.

## Working style

The person you are working with is the founder, not a programmer. He has very
little coding experience.

- Explain what you are about to do in plain language before doing it.
- Do one step at a time. Verify that step worked before starting the next.
- Never assume familiarity with git, the terminal, npm, or editors. Spell out
  commands in full and say what a successful result looks like.
- When something fails, say plainly what broke and what the recovery step is.
  Do not silently retry with a different approach.
- Prefer the simplest path that works over the most elegant one.
- Do not refactor, rename, reformat, or "clean up" code outside the scope of
  the current task.

## Git workflow

```
git checkout main
git pull
git checkout -b <descriptive-branch-name>
# ... make changes, run node --check ...
git add <specific files, never -A>
git commit -m "<what changed and why>"
git push -u origin <branch-name>
gh pr create
```

Stage files by name. Do not use `git add -A` or `git add .`.

## Deployment

Render auto-deploys from `main` after a PR is merged.

The Render dashboard spinner is unreliable — it often shows a deploy as still
in progress after the new code is already live. **Treat the live site as the
source of truth**, not the dashboard. Verify a change by loading the page.
